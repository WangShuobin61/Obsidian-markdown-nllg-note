# 应用外壳框架架构与设计报告

**项目**：sx_cleansilt_qt  
**技术栈**：Qt 6.10.3 / C++ 17 / FluentUI for Qt6  
**编写日期**：2026-08-14

---

## 一、重构动机

原始目录按**技术角色**横向分层（`auth/`、`viewmodels/`、`shell/`、`theme/`、`core/`），同一功能（如鉴权）的 QML 与 C++ 分布在多个顶层目录，修改时需要跨目录跳转，CMake target 的边界与功能边界不一致。

**重构目标**：顶层按功能内聚，功能内部保留 MVVM 分层，CMake target 与功能边界对齐。

---

## 二、架构设计原则分析

### 优势

**功能内聚，修改路径短**：修改任何功能，相关文件集中在同一目录。以鉴权为例：

```
原来：src/auth/ + src/viewmodels/authVM/ + src/core/database/（至少 3 处）
现在：src/features/auth/（1 处）
```

**CMake target 与功能边界一致**：删除一个功能 = 删一个目录 + 一行 `add_subdirectory`，不留僵尸头文件。

**QML module URI 语义清晰**：`import cleansilt.features.auth` 就是"导入鉴权模块"，不再有 `import flushell.viewmodels` 把四类毫无关联的类型打包的问题。

**依赖方向可追踪**：`app → features/* → shared`，`shared` 不反向依赖任何 feature。

**可裁剪性**：不需要某个功能整体移除一个目录，以前横向分层时需要在多个目录里分别找文件。

### 局限

**跨功能共享逻辑的归属需要主动决策**：判断原则——已经被 **≥ 2 个 feature** 实际引用，才进入 `shared/`；只有一个 feature 用的工具，放在该 feature 内部。误判会导致 `shared/` 退化成新的 `core/`。

**QML module 增多**：原来一行 `import` 解决所有 C++ 类型，现在需要按模块分写。这是"显式优于隐式"的代价，可接受。

## 五、核心模块设计

### 5.1 ShellLayout — 四区可折叠布局

布局层次（水平 SplitView 嵌套垂直 SplitView）：

```
FluSplitLayout（水平）
├── leftSlot    Loader ← leftPane，折叠时 active=false 真正释放资源
├── centerSlot  FluSplitLayout（垂直）
│   ├── centerMainSlot  Loader ← centerPane
│   └── bottomSlot      Loader ← bottomPane，折叠时 active=false
└── rightSlot   Loader ← rightPane，折叠时 active=false
```

**核心设计：折叠状态单一数据源**。

`ShellLayout` 持有 `leftVisible / rightVisible / bottomVisible` 三个属性，`ShellWindowControls` 通过 `dockTarget` 引用直接读写，不经过 `Window`，消除了原来状态复散到 Window + 标题栏 + 内容区三处的问题：

```qml
// ShellLayout.qml
property bool leftVisible:   AppPreferences.leftPaneVisible
property bool rightVisible:  AppPreferences.rightPaneVisible
property bool bottomVisible: AppPreferences.bottomPaneVisible

property Component leftPane:   null  // 不注入 → 折叠按钮自动隐藏
property Component centerPane: null
property Component bottomPane: null
property Component rightPane:  null

function toggleLeft()   { leftVisible = !leftVisible }
function toggleRight()  { rightVisible = !rightVisible }
function toggleBottom() { bottomVisible = !bottomVisible }

// 供宿主窗口推导 minimumWidth
readonly property int contentMinimumWidth: ...
```

`hasLeftPane / hasRightPane / hasBottomPane` 由 `prop !== null` 推导，没有注入内容的区，对应折叠按钮自动隐藏。

状态持久化：`onXxxVisibleChanged` 直接回写 `AppPreferences`。

### 5.2 ShellWindowControls — 折叠按钮

通过 `dockTarget` 属性引用 `ShellLayout`，不依赖宿主 `Window` 实现细节：

```qml
property var dockTarget: null

FluIconButton {
    visible: dockTarget !== null && dockTarget.hasLeftPane
    iconColor: _dockColor(visible && dockTarget.leftVisible)
    onClicked: dockTarget.toggleLeft()
}
```

`dockTarget` 为 `null` 时三个折叠按钮整体隐藏，向后兼容。

### 5.3 主窗口内容区（MainWinFunction）

`centerPane` 挂载 `MainWinFunction`，包含四个等宽标签页：

| 标签 | 组件 | 说明 |
|------|------|------|
| D435 相机 | `Camera1Tab.qml` | RealSense D435 RGB 取流视图（待现场设备验证） |
| 功能预留 1 | `DemoTab1.qml` | 随机写入日志/消息的测试按钮 |
| 功能预留 2 | `DemoTab2.qml` | 同上，独立文本集合 |
| 数据库 | `DatabaseTab.qml` | 系统事件表格查询、分页、导出 xlsx、二级删除 |

每个标签页均可右键或长按（0.7 秒）在独立窗口中打开，由 `TabContentBase` 统一实现。

### 5.4 底部停靠区（BottomDockPanel）

`bottomPane` 挂载 `BottomDockPanel`，使用 `FluSplitLayout`（水平）左右分割：

- **左**：`SystemEventPanel`（来自 `systemevents` 模块）—— 实时滚动日志
- **右**：`SystemEventPanel`（消息模式）—— 实时滚动消息

### 5.5 触摸屏悬浮球（FloatingBall）

`DragHandler` 全屏自由拖拽，位置以比值（`xRatio / yRatio`）落盘：

```qml
// AppPreferences 新增字段
property bool floatingBallEnabled  // 设置面板开关，默认 false
property int  floatingBallSize     // 0~100，映射到实际像素大小
property real floatingBallXRatio   // 0~1，相对父容器宽度的位置比
property real floatingBallYRatio   // 0~1，相对父容器高度的位置比
```

父容器尺寸变化时自动夹回边界，随窗口缩放正确恢复位置。

### 5.6 Tour — 新手导览自适应

`Tour.qml` 用计算属性 `dockSteps` 动态构建折叠步骤，**只有对应按钮实际可见时才纳入步骤**：

```qml
readonly property var dockSteps: {
    const list = []
    if (targetDockLeft && targetDockLeft.visible)
        list.push({ title: qsTr("左侧栏"), ... })
    if (targetDockBottom && targetDockBottom.visible)
        list.push({ title: qsTr("底栏"), ... })
    if (targetDockRight && targetDockRight.visible)
        list.push({ title: qsTr("右侧栏"), ... })
    return list
}
steps: dockSteps.concat(baseSteps).concat(extraSteps)
```

## 七、派生项目使用指南

### 最小改造步骤

1. 全局替换 URI 前缀 `cleansilt` → 新项目名
2. 在 `Main.qml` 的 `ShellLayout` 四个插槽中替换占位 `DemoPanel` 为业务组件：

```qml
ShellLayout {
    id: shellLayout
    anchors.fill: parent
    visible: UserSession.isLoggedIn

    leftPane:   Component { MyLeftPanel {}   }  // 不需要的区不写，折叠按钮自动消失
    centerPane: Component { MyMainContent {} }
    bottomPane: Component { MyStatusBar {}   }
    rightPane:  Component { MyControlCard {} }
}
```

3. 给 `ShellTitleBar` 接上 `dockTarget: shellLayout`（模板中已完成）。

### 扩展业务偏好

不要改 `AppPreferences.qml`，另建 `XxxPreferences.qml`（同样 `pragma Singleton`，同样 `Settings { category: "..." }`），保持基座偏好与业务偏好内聚分离。

## 八、已知遗留告警

```
qrc:/qt/qml/FluentUI/Controls/FluShortcutPicker.qml:15:
    Unable to assign [undefined] to FluHotkey*
```

**根因**：FluentUI 源码 `FluShortcutPicker.qml` 声明了 `property FluHotkey syncHotkey: undefined`，QML 引擎在每次实例化时告警。  
**影响**：零。本项目从未使用 `syncHotkey`，该 handler 永远不会触发。  
**结论**：正确修法需维护 FluentUI patch，性价比极低，维持现状。

## 九、架构评估：为何不采用 Qt 插件式开发

| 维度 | 编译期模块（当前方案） | Qt 插件式 |
|------|----------------------|-----------|
| 新增功能成本 | 改 CMake + 改 Main.qml + 全量重编 | 编译一个 `.so`，放进目录重启生效 |
| 主程序耦合 | 直接依赖具体类型 | 只依赖抽象接口 |
| ABI 稳定性负担 | 无 | 重：接口变则所有插件必须同版本重编 |
| 单人/单产品效率 | 高 | 低（多付出接口设计+版本管理成本） |

**结论**：插件式的收益在于"主程序发布后第三方独立扩展"。当前场景是自己克隆新项目（编译期复用），不满足插件式的价值前提。`ShellLayout` 的 `Component` 插槽已提供等价的可替换性，且有完整编译期类型检查。
